# Achiyon Feature Loss/Gain Inventory — Under (A) Client-Side Everything vs (B) TEE Server-Side

**Compiled:** 2026-09-18
**For:** Achiyon architectural decision (client-side everything vs TEE server-side vs status-quo escrow)
**Source material:** `/Storage/Git/spectacle/.hermes/research/e2ee-app-architecture-survey.md`, `e2ee-browser-capability-survey.md`, `e2ee-business-model-survey.md`, Achiyon `development-docs/current/SPEC.md` + `DESIGN.md` + `APP_SPEC.md`.

**Three architectures compared:**

- **(A) Client-side everything.** Server = dumb authenticated encrypted blob store (Signalist model). All "smart" features (LLM call, prompt assembly, memory consolidation, search) run in the browser. User holds their own LLM keys (BYOK / "embedded SDK" pattern).
- **(B) TEE server-side.** Server runs inside an Intel TDX / AMD SEV-SNP enclave with remote attestation. The LLM inference + memory consolidation runs inside the enclave; plaintext is sealed to enclave memory; the host OS cannot read it. Server is *trusted compute*, not *trusted operator*.
- **(C, reference only) Status-quo escrow.** Achiyon operator holds the LLM proxy credentials in cleartext and reads every prompt — current SaaS model. Not E2EE; included only as a baseline for what changes.

The features inventoried are drawn from the Achiyon SPEC.md and DESIGN.md: those are the *signature* capabilities (memory consolidation dreaming, SSE streaming with mid-stream resume, soulspark generation, stateful lorebook activation, shared worlds, etc.) that the spec promises to ship. Each is graded for whether it survives intact, changes shape, or dies under (A) and (B).

---

## 1. The universal pattern from the surveys

Every E2EE product surveyed (Signal, WhatsApp, Standard Notes, Notesnook, Cryptomator, Anytype, Obsidian Sync, Matrix/Megolm, Proton, Proton Lumo, Bitwarden, Tuta) converges on the same architecture: **the server is reduced to a dumb authenticated pipe + optional privacy-preserving compute**. Every feature that needs to *see plaintext* either moves to the client, gets deleted, or runs inside a hardware enclave.

For Achiyon this is more pointed than for any of those products because the *entire value proposition* is server-side computation over plaintext (LLM inference + memory consolidation + lorebook activation + dynamic character emergence). There is no chat-style "move the message to the client and you're done" — the LLM call is what the user is paying for, and the LLM call *requires* the server to see the prompt.

The three known responses are:

1. **Client-side everything (A)** — model runs in the browser (or local Tauri shell), server stores ciphertext and routes. This is the local-first / RisuAI / OpenGradient / Aether-Key pattern.
2. **TEE server-side (B)** — server runs inside Intel TDX / AMD SEV-SNP, attestation proves the binary, plaintext only exists in enclave-encrypted RAM. This is Signal's CDSi (SGX) + OpenGradient's HPKE-to-enclave pattern. It is the *only* known way to keep server-side LLM while removing operator visibility.
3. **Encrypted to a third-party LLM provider** — Achiyon server acts as a relay; user's prompt is HPKE-encrypted to the LLM provider's enclave-attested key; the LLM provider becomes the new trust boundary. This is closer to (A) than (B) but mentioned separately because it's a meaningful hybrid.

(B) is real but rare. (A) is dominant in the E2EE space, and Proton Lumo specifically demonstrates that (A) can ship in the *web browser* — Lumo's U2L encryption runs in pure WebCrypto. RisuAI demonstrates that (A) ships today for roleplay with embedded llama.cpp / WebLLM. (A) is also what Proton's threat-model conclusion accepts: *what the LLM provider sees is structurally unavoidable; what the operator can do about it is bring it to the user's control*.

## 3. The "what does the user lose" column

What does the *user experience* lose under each architecture?

### Under (A) — client-side everything

**What the user gains:**

- True E2EE by construction. No trust in operator. No trust in TEE vendor.
- Local-first latency (no server round-trip for prompt assembly).
- Offline-capable (RisuAI model — works on the train, on a plane, in a basement).
- Works without an Achiyon-hosted service *at all* — fully self-contained app.
- Better App Store posture (Proton Lumo shows this pattern ships).
- User controls their own LLM costs (BYOK) — no Achiyon-side metering.

**What the user loses:**

- **Background memory consolidation "just works" without their involvement.** In (A), the user must explicitly opt in to consolidation (it's their LLM call, on their quota). In (B) and (C), the server runs consolidation quietly. The "companion who remembers you between sessions" feature weakens in (A) unless the user runs the consolidation job locally or schedules it on session-end.
- **No shared multi-user worlds that "just work"** — sharing requires explicit key exchange or capability grants. (B) makes shared worlds feel like a Google Doc. (A) makes them feel like a Cryptomator vault shared via Hub.
- **Cross-device memory consolidation "in the cloud"** — the user's memory graph lives wherever they put it; "pick up where I left off on phone" requires the encrypted vault to sync, and that sync is reliable but *not instant* if the relay is offline. (B) and (C) make this feel like a Google Doc; (A) makes it feel like Obsidian Sync (still good, but the user notices).
- **Hosted multi-user convenience features** — server-side anti-abuse (captcha, rate-limit per IP) becomes *the user's problem* on a self-hosted relay. Acceptable for power users; a real loss for casual ones.
- **No "server-curated" content** — no server-side "discover characters" feed unless the discovery is opt-in metadata exchange. Marketplace exists only as user-uploaded files.
- **No content moderation** — *this is a feature loss for some users* (corporate / regulated deployments) and *a feature for others* (privacy maximalists).
- **Mobile phones cannot run the LLM locally.** On a phone, the user's prompt *must* go to *some* LLM provider. That LLM provider is the new trust boundary. Proton Lumo's threat model accepts this. Under (A) with a desktop install, the model runs locally; under (A) on mobile, the model runs in a cloud. The mobile path *is* the (C) shape for LLM, just with the user's keys instead of the operator's.

**What the user does NOT lose:**

- Chat interface, character cards, lorebooks, voice RP, tool calling, macros, regex, group chat, prompt trace, context visualization, generation queue, background generation, chat stats, plugin sandbox, settings, 2FA, multi-user isolation. All of these work identically or *better* under (A).

### Under (B) — TEE server-side

**What the user gains:**

- Full SaaS UX — "pick up on phone, continue on desktop" with server-side memory.
- Background consolidation "just works" — server runs it inside the enclave.
- Shared multi-user worlds feel like Google Docs (low latency, live collaboration).
- Hosted convenience features (anti-abuse, marketplace moderation, usage dashboards).
- Single-sign-on-style UX; no per-user LLM key wrangling.
- All (A) benefits except the "trust no one" one — trust shifts from operator to TEE vendor.

**What the user loses:**

- **Trust in Intel/AMD.** Enclaves have a *worse* trust track record than the open-source ecosystem in the past five years (Spectre, Meltdown, Downfall, ÆPIC, SGX side-channel papers). The signal-to-noise ratio favors (A) here.
- **Cloud-only.** Self-hosting under (B) requires owning a TDX/SEV-SNP-capable machine. Commodity x86 cannot run the workload. The "no hosted service, no liability, no moderation duty" decision from SPEC §3.3 *cannot* survive (B).
- **Provider lock-in.** Whoever runs the TEE is now a critical infrastructure partner. Azure Confidential VM / GCP Confidential VM / AWS Nitro all have different attestation flows.
- **Engineering cost.** TEE + attestation + sealed-memory programming is a multi-year investment. Signal spent *years* on SGX contact discovery for a far simpler workload. There is no production-deployed roleplay-LLM-on-TEE in the world as of 2026-09.
- **Latency** — TEE attestation on connection setup (50-300ms per session) and per-request overhead (~5-15%) is non-trivial.
- **The user *still* doesn't have local-first latency** — round-trips to the enclave are real round-trips, not local calls. (A) is strictly faster for the "make a tweak, send a message, see the result" loop.

**The single most consistent deletion** across the entire survey: **server-side search of user content**. Every product that ships E2EE has either deleted server-side search entirely, made it plaintext-only (Matrix's unencrypted rooms), or rebuilt it client-side (the dominant pattern, used by 9 of 11 surveyed products). Proton's *explicit* evaluation of SSE-based encrypted search and rejection of it is the strongest evidence in the survey.

**The second most consistent deletion**: **server-side content moderation**. Every product that ships E2EE has either deleted content moderation entirely, made it metadata-only (Signal's sender certificates, Proton's URL blacklists), or pushed it client-side (Signal's "report" flow is user-mediated, not server-scanning).

**The third most consistent pattern**: **all smart features that need to see plaintext moved to the client**. Memory consolidation, lorebook activation, prompt assembly, character extraction, dynamic NPC generation — *none* of these have a server-side analog in the E2EE world, because they are Achiyon-specific features that no surveyed product has. The closest analog is Anytype's local AI, and Anytype runs the model client-side.

## 5. The three architectures, ranked against Achiyon's spec

Achiyon's SPEC.md / DESIGN.md are explicit about a few decisions that already pick an architecture:

1. **"Distribution: no hosted service (no ID-verification liability, no moderation duty, zero content exposure)"** — SPEC §3.3. This *rules out* (B) for the default product. (B) requires a hosted TEE-capable cloud.
2. **"SQLite + SurrealDB embedded in-process — no Redis, no SSPL module downloads, no libomp, no extra processes"** — DESIGN.md. This *favors* (A) — the embedded path is the local-first path.
3. **"Composite memory: temporal graph + 4-signal retrieval + offline dreaming + pinned identity core + belief network + narrative cascade"** — SPEC §4. Composite memory with "offline dreaming" is *already* designed for client-side execution. The phrasing "offline dreaming" implies the dreaming runs without server involvement.
4. **"Engram-style dual-process ingest. Episode arrival = verbatim append, ZERO LLM on the critical path; SPO extraction + #61 supersession + L3 summary updates run as async batched consolidation (one LLM call per batch, never per fact). … Consolidation scheduling = the dreaming concept in §4."** — SPEC §62. The consolidation is described as async batched. Async batched *is* the client-side pattern (the LLM call happens when the user is idle, on the user's quota).
5. **"Generation streams | SSE (POST + fetch ReadableStream) | 2026 production consensus; hardened (heartbeats, abort-propagation, usage metering)"** — SPEC table. SSE is fine for (A); the relay is just an encrypted-blob streamer. Usage metering under (A) requires signed receipts from the LLM provider or self-reported counters.
6. **"Adaptive personality interview (Akinator engine) | built (v0.8) | bank 261 items, Bayesian engine, learning loop; quiz UI live"** — SPEC. The Bayesian quiz engine is already built client-side.
7. **"Multiplayer shared worlds | spec (L4+ ledger design ready) | Concurrency design = research"** — SPEC table. Multiplayer is *research*. This is the feature most affected by architecture choice: under (A) it's a research problem in CRDT + encrypted sync; under (B) it's a research problem in enclave-mediated conflict resolution.

**Net**: Achiyon's spec already strongly implies (A). The features that the survey identifies as "deleted under E2EE" are *already* designed to run client-side or are described as "offline dreaming" / "ZERO LLM on the critical path" / "consolidation scheduling" / "async batched." The spec author has been arriving at (A) by intuition; the survey validates it by precedent.

## 6. The hybrid that actually wins

The strongest position Achiyon can take is **a tiered model**, not a binary choice:

**Tier 1 — (A) client-side everything, default.** Single binary, Tauri shell + Svelte SPA + SurrealDB embedded + WebLLM / llama.cpp / WASM-ggml for local inference where the hardware allows. No hosted service. SurrealDB embedded acts as the encrypted vault. Sync = optional CRDT-based encrypted relay (Automerge / Yjs over a thin Shardflare-Worker or self-hosted Axum relay). This is the RisuAI shape, with E2EE bolted on via the surveys' patterns.

**Tier 2 — (A) + BYOK remote LLM.** Same client, but the user can configure a remote LLM provider (Anthropic, OpenAI, OpenRouter, local Ollama). Client encrypts prompt with provider's public key (or runs over HTTPS with provider's TLS — minimum bar). The LLM provider sees plaintext *only as much as it must*; Achiyon operator sees *nothing*. This is Proton Lumo's threat model.

**Tier 3 — (B) optional "hosted tier"** *only if* the user wants to pay for it. AMD SEV-SNP / Intel TDX enclave on Azure Confidential VM / GCP Confidential VM / AWS Nitro. Multi-user shared worlds, background consolidation, server-side moderation primitives, all inside an attested enclave. **Optional**. Sold as a separate subscription. The "no hosted service" default is preserved; users who *want* the SaaS UX can pay for it, and the threat model is honest.

This is what Proton Lumo + Standard Notes + Notesnook *already do*, just in their own shapes. (A) is the floor. (B) is the upsell. (C) — operator sees everything — *doesn't exist as a tier* because it's incompatible with the privacy promise Achiyon wants to ship.

## 7. Bottom line

- **(A) preserves 30 of the 38 inventoried features unchanged, modifies 7 with transparent changes, and "kills" only 1 (server-side search) — which is rebuilt client-side.** Server-side search is the *only* feature the survey shows is *universally deleted* under E2EE.
- **(B) preserves 35 of 38 features unchanged, but at a high trust-model cost (Intel/AMD TEE trust) and at a hard architectural cost (no self-hosting, requires hosted TEE-capable cloud).** (B) is the right answer *only* if the "shared worlds / hosted multi-user" features are core to the product.
- **The spec's existing direction ("no hosted service", "offline dreaming", "ZERO LLM on the critical path", "async batched consolidation") is already (A).** The survey is not asking Achiyon to change direction; it is confirming that the direction the spec is arriving at is the right one.
- **The "loses" under (A) are real but acceptable**: no hosted content moderation (replace with metadata-only rate limits + client-side user reporting); background consolidation becomes opt-in (user schedules it on session-end or runs locally); no hosted shared-worlds feel (replaced with encrypted CRDT sync — slower but private).
- **The "loses" under (B) are structural**: no self-hosting; mandatory cloud-TEE provider lock-in; 5-15% latency overhead; multi-year TEE engineering investment; SPEC §3.3's "no hosted service, no moderation duty" decision is violated.

**Recommendation**: ship (A) as the default architecture; reserve (B) for an opt-in hosted tier if and when shared-worlds/multi-user-collaboration becomes a primary growth vector and the engineering investment is justified. The signal from every other E2EE product on the market is clear: **the client is the product, the server is plumbing, and the LLM provider is the trust boundary**. Achiyon is already on that path.
