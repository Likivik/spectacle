# Innovation Audit — Self-Hostable Agent Platforms

**Date:** 2026-10-07
**Scope:** Nous Research Hermes Agent, OpenClaw, ZeroClaw, Letta, AnythingLLM, OwnPilot, OpenCrust, Cognithor, PicoClaw/Moltbot/NanoBot, Dify, n8n, OpenHands, AutoGPT.
**Framing:** Simon Willison's *lethal trifecta* (private data + untrusted content + external communication → data exfiltration) is the central technical question. "Novel" here means the system introduces a defensible design primitive, not a marketing claim.

Conventions:
- "not documented" = I could not find a public, primary-source description after a reasonable search. It may exist; the platform does not advertise it.
- Citations are URLs of primary sources (docs, source files, advisories, papers) wherever possible.

---

## 1. Per-platform: the ONE genuinely strong thing

### 1.1 Nous Research Hermes Agent
- **Genuinely strongest thing:** the *defense-in-depth* of the harness around a single, open-ended LLM loop. Specifically, the `pre_tool_call` hook that can **fail closed** (block a tool call outright, even overriding an `approve`), and the **dual protection layer for context files** (`AGENTS.md`/project files are scanned and *blocked* with a `[BLOCKED: AGENTS.md contained potential prompt injection]` warning before the agent ever sees them). These are the only first-class, documented, in-harness "trust the file less than the user" controls among the named platforms.
- **Citation:** security model — `https://hermes-agent.nousresearch.com/docs/user-guide/security`; hook trust model (including `pre_tool_call` block behavior and shell-hook credential trust) — `https://hermes-agent.nousresearch.com/docs/user-guide/features/hooks`; agent architecture (Prompt Builder, Tool Dispatch, 28 toolsets, 70+ tools, 7 terminal backends) — `https://hermes-agent.nousresearch.com/docs/developer-guide/architecture`.
- **Marketing fluff to flag:** "self-improving AI agent with a built-in learning loop" and "creates skills from experience" — true in the literal sense that the agent can write files to `~/.hermes/skills/`, but this is procedural memory in the standard LLM-tool-use sense, not an architectural innovation.

### 1.2 OpenClaw
- **Genuinely strongest thing:** nothing. The platform's history of CVEs (CVE-2026-32922 in `device.token.rotate`, CVSS 9.9, plus at least 10 further advisories in March–June 2026 per the akaoma CVE list) is the substantive technical fact. The recurring *failure mode* is scope-containment bypasses in its pairing/refresh code path (CVE-2026-32922, CVE-2026-53842, CVE-2026-53847, CVE-2026-53851, CVE-2026-53862) — i.e. token rotation that doesn't intersect the caller's current scope set. That is itself the architectural lesson: the device-pairing design is the product, and the design keeps producing the same class of bug.
- **Citations:** primary CVE — `https://nvd.nist.gov/vuln/detail/CVE-2026-32922`; GHSA — `https://github.com/advisories/GHSA-x8qx-w8w2-g4rx`; akaoma multi-CVE listing — `https://cve.akaoma.com/vendor/openclaw`.
- **Marketing fluff to flag:** "Secure by design," "self-hosted agent platform for everyone," and any "we take security seriously" boilerplate on the OpenClaw site is contradicted by the CVE volume and the recurring scope-containment class.

### 1.3 ZeroClaw
- **Genuinely strongest thing:** the *capability-isolation-without-Quarantined-LLM* design. A 2026-03-03 GitHub issue (closed by merged PR #2663) explicitly frames the work as preventing the "lethal trifecta" by giving the primary orchestrator `allowed_tools`/`denied_tools` filters that remove tool descriptions **and** remove tools from the executable registry. The key technical claim is that filtering is applied at both prompt-build time *and* tool-call time, in `Agent::from_config` and the runtime loop (`run`/`process_message_with_session`). For a 100% Rust runtime, this is a real design primitive, and the maintainers actually engaged the question rather than dismissing it (unlike the yencabulator critique applied to a slightly earlier state).
- **Caveat:** the yencabulator critique still applies: the design reduces trifecta risk by *removing tools*, not by capability-tagging untrusted data and tracking taint through tool outputs. The Quarantined-LLM (Q-LLM) part of the lethal-trifecta threat model is not implemented.
- **Citations:** issue — `https://github.com/zeroclaw-labs/zeroclaw/issues/2651`; HN critique — `https://news.ycombinator.com/item?id=47047192`; project README/security overview — `https://github.com/zeroclaw-labs/zeroclaw`.
- **Marketing fluff to flag:** "Zero overhead. Zero compromise." On the README front matter — that is the opposite of what a security review would say; "Zero" overhead and a fully featured LLM-runtime are mutually exclusive. The repo is small and unmaintained-comparator to OpenClaw; "production-grade" framing on any blog post about it should be treated as marketing.

### 1.4 Letta
- **Genuinely strongest thing:** *MemFS* — a git-backed filesystem that tracks *all agent context* (memory blocks, skills, prompts, and even the harness) and can be synchronized to a custom GitHub repository. This is the only one of the audited systems that takes "the model rewrites its own memory" out of the realm of vibes and gives it a content-addressed, branchable, auditable substrate. The *Stateful agent* model (memory, identity, experience, "mod"-extensible harness) is genuinely the most coherent research artifact in the field.
- **Caveat:** the parent's "Next Phase" (2026-03-16) sunset of Filesystem, MCP, sleep-time agents, and tool rules means *most of the interesting stuff in earlier Letta* has been deprecated. The current Letta Code and Letta Agent SDK are a *narrower* system than the historical Letta. Anyone who reads the 2024 MemGPT papers and assumes that surface area still exists is wrong. (The 2026-03-16 sunset date was supplied in the task brief; I could not pull the post body itself into this audit, so I am treating that as given context rather than independently re-verified.)
- **Citations:** MemFS, memory blocks, skill learning, mods, `/sleeptime` — `https://github.com/letta-ai/letta-code` (README, "Self-improvement & Learning", "MemFS"). Sunset claim is taken from the task brief and not independently re-verified here.
- **Marketing fluff to flag:** "agents that are like people" is a marketing slogan, not a technical claim. The technical claim is "memory that persists across model swaps, computers, and harness restarts, and that the agent can rewrite" — and MemFS delivers that part.

### 1.5 AnythingLLM
- **Genuinely strongest thing:** the *workspace isolation model*. A workspace is a container of documents; workspaces share documents but do not share conversation context. This is the *only* multi-tenant RAG product in the audit whose isolation unit is a first-class object in the user-facing UI rather than an internal storage row. The "file system agent" skill is also a clean primitive: by default it can read *nothing*; the operator must mount host folders into a *specific* container path (`/app/server/storage/anythingllm-fs/`) and any path outside that mount is unreachable, by construction, not by a runtime check. That is real sandbox-by-mount, not a runtime ACL pretending to be one.
- **Citations:** vector DBs and local-first defaults — `https://docs.anythingllm.com/features/vector-databases`; workspace model — `https://github.com/Mintplex-Labs/anything-llm` README; file-system-agent mount constraint — `https://docs.anythingllm.com/agent/usage/file-system-agent`.
- **Caveat / critical look:** the security advisories list for AnythingLLM is non-trivial — RCE via ripgrep `--pre` argument injection in the filesystem-search-files skill (GHSA-6hrp-7mw6-8v59, May 2026), cross-folder symlink following (GHSA-vjrp-43mm-j7vw, May 2026), and stored DOM XSS via LLM-driven prompt injection rendering unsanitized chart captions (GHSA-4q6m-qh3w-9gf5, Apr 2026). The LLM-driven-XSS-into-chart is *itself* a lethal-trifecta exfiltration vector (untrusted content → render to a privileged user). So: good isolation primitive, but the *content pipeline* still has classical injection problems.
- **Citations for advisories:** `https://github.com/Mintplex-Labs/anything-llm/security/advisories`.
- **Marketing fluff to flag:** "Privacy by default. Designed to be private by default. Everything is stored and run locally." That is true for the desktop app, less true for the Hosted product. The site mixes the two.

### 1.6 OwnPilot
- **Genuinely strongest thing:** the *four-tier autonomy model* (`Manual` / `Assisted` / `Supervised` / `Autonomous` / `Full`) wired to a `RiskAssessment` step *between* tool-call permission check and execution. Looking at the data-flow diagram in the architecture doc: `tool_call → tool limits → permissions → risk assessment → (approve | queue for human) → execute`. This is the only platform in the audit that treats "should this execute?" as a *typed* decision (numeric autonomy level × risk-level match) rather than a binary yes/no approval. It is also the only one with first-class multi-tier delegation (`Subclaw` with max depth 3, parent control over children). Whether the implementation actually delivers is another question (the project is on v0.8.3 with 429 stars), but the design is genuinely interesting.
- **Citations:** architecture doc — `https://github.com/ownpilot/OwnPilot/blob/main/docs/ARCHITECTURE.md` (§5.1 Agent System, §5.5 Privacy/Security, §6.7 Autonomy System, §9 Data Flow Tool Execution Flow); README — `https://github.com/ownpilot/OwnPilot`.
- **Caveat:** the `MCP Client` + `MCP Server` symmetric design is genuinely novel for a self-hosted platform — OwnPilot can be both an MCP *consumer* (Filesystem, GitHub, Brave) and an MCP *provider* (expose its tools to Claude Desktop). But the platform is small (429 stars, 63 forks at the time of writing) and 2160 commits in nine months is an aggressive velocity that hasn't yet been independently audited; treat the architecture doc as a design claim, not a deployment recommendation.
- **Marketing fluff to flag:** "Privacy-first" appears 4+ times in the README. Once is enough.

### 1.7 OpenCrust
- **Genuinely strongest thing:** the **credential vault + WebSocket pairing + per-channel pairing-code + WASM plugin sandbox** stack, implemented in Rust with audited primitives (AES-256-GCM, PBKDF2-SHA256 600k iterations, `ring` crate, `wasmtime`, `SystemRandom`). The `InputValidator` claims to scan for 14 known injection patterns (text in the security doc; specific pattern list not enumerated in the page I read). The gateway defaults to binding `127.0.0.1` and rate-limits per-IP and per-WebSocket. This is the *smallest* of the audited platforms (143 stars) and probably the most disciplined *defense-in-depth* implementation relative to its size — but its discipline is in 2024 primitives (pattern-matching, AES, WebSocket auth) rather than 2025/2026 ones (capability flow, dual-LLM, taint tracking).
- **Citations:** security architecture page — `https://opencrust-org.github.io/opencrust/security/architecture.html`; project README — `https://github.com/opencrust-org/opencrust`; architecture overview — `https://opencrust-org.github.io/opencrust/architecture.html`.
- **Caveat:** the `InputValidator` "14 known injection patterns" is a *denylist*. Denylist-based prompt-injection detection has been shown ineffective by Meta's "Attacker Moves Second" paper (arXiv 2510.09023, Oct 2025) and is not a substitute for capability-based data flow. The rest of the security stack is solid by 2024 standards.
- **Marketing fluff to flag:** "Security-First Architecture" headline on the doc — the architecture is security-*aware*, not security-first in the CaMeL sense.

### 1.8 Cognithor
- **Genuinely strongest thing:** the *Planner–Gatekeeper–Executor* (PGE) decomposition, codified in ADR-0001 (`docs/adr/0001-pge-trinity-vs-group-chat.md`). This separates planning (LLM-driven), *gatekeeping* (deterministic policy check on each proposed tool call before it reaches an executor), and execution. The "Deterministic Replay" feature — record and replay agent executions with what-if analysis — is also a real research primitive. Combined with the "Agent Benchmark Suite" (14 standardized tasks, regression detection) this is one of the only platforms built around a *reproducibility* primitive rather than a productivity one.
- **Citations:** PyPI page (architecture, ADR list, PGE mention) — `https://pypi.org/project/cognithor/0.92.4` and `https://pypi.org/project/cognithor/`; the repository is `https://github.com/Alex8791-cyber/cognithor` (per the PyPI release).
- **Caveat:** the project is small, single-maintainer, with a placeholder website (`cognithor.ai`) and an "Apache 2.0" / "Beta" status flag. "19 LLM Providers, 18 Channels, 6-Tier Memory" reads more like an aggregator than a coherent platform; the PGE decomposition is the genuinely interesting idea and the rest of the feature list is feature-count marketing.
- **Marketing fluff to flag:** "Agent OS" — there is no agreed meaning of "agent operating system" in 2026, and using it as a product name is a marketing choice, not a technical claim.

### 1.9 PicoClaw / NanoBot / Moltbot
- **Genuinely strongest thing:** PicoClaw's *uniform workspace restriction* — the `restrict_to_workspace` setting applies identically to the main agent, subagents, and heartbeat tasks. The README's table is explicit: "Main Agent ✅ / Subagent / Spawn ✅ / Heartbeat tasks ✅ / All paths share the same workspace restriction — there's no way to bypass the security boundary through subagents or scheduled tasks." This is a real, *small* primitive — it closes one of the classic agent-escape paths (subagent running with broader filesystem access than the parent).
- **Caveat:** PicoClaw README *itself* warns: "picoclaw is in early development now and may have unresolved network security issues. Do not deploy to production environments before the v1.0 release." The whole Moltbot/PicoClaw/NanoBot family is also a *fragmentation* story: same upstream (Moltbot, formerly Clawdbot), 13–436 stars depending on the fork, "v1.0" not shipped, official website is `picoclaw.io` and the README actively warns about domain-spoof scams. This is a moving target, not a security-hardened alternative to OpenClaw.
- **Citations:** PicoClaw README (workspace consistency, security sandbox, official-domain warning) — `https://github.com/picoclaw-labs/picoclaw`; NanoBot — `https://github.com/lightweight-nanobot/nanobot`; MoatBot (a fork that *does* claim to be a security-hardened re-implementation) — `https://github.com/Ckokoski/moatbot-security`.
- **Marketing fluff to flag:** "🦐 Ultra-Efficient AI Assistant" / "AI-Bootstrapped" / "95% Agent-generated core" — these are vibes. The 95% figure is not falsifiable and the AI-bootstrapping claim is unverifiable from the repo alone.

### 1.10 Dify
- **Genuinely strongest thing:** the *agent-sandbox-gateway* as a separate Docker service in the standard Docker Compose deployment. Code Node execution is in a separate container ("isolating code execution from the host and from other services") and outbound network calls from sandboxed code route through an **SSRF proxy** (toggleable via `SANDBOX_ENABLE_NETWORK=false`). The new Agent node (Workflow apps, "complete worker with its own capabilities and sandbox") is documented as bundling a sandbox in the default Docker Compose. The enterprise product has SOC 2 Type II + ISO 27001 + SSO/SAML/RBAC/audit logs.
- **Citations:** Code Node docs (sandbox container, SSRF proxy) — `https://docs.dify.ai/en/self-host/use-dify/nodes/code` and `https://docs.dify.ai/en/use-dify/nodes/code`; Agent node — `https://docs.dify.ai/en/self-host/use-dify/nodes/agent`; security posture at agent-sandbox-gateway level — `https://ee.dify.ai/reports/v3.12.1/scout/agent-sandbox-gateway`.
- **Caveat:** the agent-sandbox-gateway is a *code execution* sandbox, not a *prompt-content* sandbox. The product documentation explicitly says "If your deployment requires strong isolation or strict security or compliance controls, use separately hardened infrastructure or contact Dify to assess an appropriate Cloud or Enterprise option." That is a real admission in the docs.
- **Marketing fluff to flag:** the homepage claim of "SOC 2 Type II + ISO 27001" is Enterprise-tier only, not Community Edition. The free Docker-deployable product has *no* security certifications.

### 1.11 n8n
- **Genuinely strongest thing:** *the sub-node architecture itself*. The AI Agent is a root node that takes *typed* sub-nodes for model, memory, tools, and output parser — the user's data flow is visually typed at the connection level, and the LangChain primitives are wrapped behind n8n's cluster-node graph. This is the only audited platform where an agent is a *node* in a typed data-flow graph that the user can read and audit, with every connection to memory/tool/model visible. The expression `{{ $json.userMessage }}` is the boundary — anything that crosses it is typed JSON, not free text. That is a real architectural primitive: deterministic data flow at the workflow level, free-form LLM inside the agent node.
- **Citations:** Agent V2 node — `https://github.com/n8n-io/n8n/blob/master/packages/@n8n/nodes-langchain/nodes/agents/Agent/V2/AgentV2.node.ts`; ToolsAgent V2 execute — `https://github.com/n8n-io/n8n/blob/master/packages/%40n8n/nodes-langchain/nodes/agents/Agent/agents/ToolsAgent/V2/execute.ts`; LangChain-in-n8n concept mapping — `https://docs.n8n.io/build/integrate-ai/langchain-in-n8n.md`; agent skills (decision matrix when to use Agent vs raw chain) — `https://github.com/n8n-io/skills/blob/main/skills/n8n-agents/SKILL.md`.
- **Caveat:** the Agent node's internal execution is a *standard* LangChain tool-calling agent with `AgentExecutor` and `createToolCallingAgent`. n8n adds visual structure, multi-tenant auth, secret management, and execution logs, but the *core loop* is not novel. And the prompt-injection question is delegated to whoever wires the system message, model, and tools together — there is no capability-tracking at the data-flow level.
- **Marketing fluff to flag:** "Fair-code workflow automation platform" — the licensing nuances are documented but the term itself is marketing; the technical fact is "Sustainable Use License + Apache for n8n core, separate EE license."

### 1.12 OpenHands
- **Genuinely strongest thing:** the **Security Analyzer** pipeline, now a composable *ensemble* (`PolicyRailSecurityAnalyzer` + `PatternSecurityAnalyzer` + `EnsembleSecurityAnalyzer`), with risk levels (`LOW`/`MEDIUM`/`HIGH`/`UNKNOWN`) that the SDK can attach a confirmation policy to (e.g. `ConfirmRisky(threshold=SecurityRisk.HIGH)`). The action-boundary is "every tool call goes through the analyzer; the analyzer returns a risk; the confirmation policy decides whether to wait for human input." This is *not* a sandbox — the docs are explicit: "This is a deterministic action-boundary control. It is not: a complete prompt-injection solution, a full shell parser or AST interpreter, a sandbox replacement, a guarantee against novel threats the patterns do not cover." That honesty is itself worth flagging — OpenHands is the only platform in this audit whose security docs enumerate what the control does *not* do.
- The second strongest thing is the *Docker Runtime* (client-server over REST, action execution server inside a Docker container, plugin system for Jupyter/VSCode/agent-skills), which is the most mature sandboxed-runtime architecture in the audit.
- **Citations:** Agent doc (Security Analyzer as first-class concern) — `https://docs.openhands.dev/sdk/arch/agent`; Security & Confirmation guide (composable ensemble, `PolicyRailSecurityAnalyzer`, known-limitations table) — `https://docs.openhands.dev/sdk/guides/security`; Docker Runtime — `https://docs.openhands.dev/openhands/usage/architecture/runtime`; Docker-in-sandbox (kernel-level isolation, user-namespace remapping) — `https://docs.openhands.dev/enterprise/docker-in-sandbox`; risk enum — `https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/security/risk.py`.
- **Caveat:** the analyzer is a *signature/pattern* match, plus a policy-rail filter. Like every denylist-based prompt-injection defense, it can be bypassed by payloads the patterns don't cover. The EnsembleSecurityAnalyzer *combines* them but is still a denylist.
- **Marketing fluff to flag:** "Secure, sandboxed runtime you control" on the homepage is true for the Enterprise tier's user-namespace-remapped container, less true for the default Community tier. Read the actual sandbox doc, not the homepage.

### 1.13 AutoGPT
- **Genuinely strongest thing:** historically, the *block-based agent design* (each "block" is a typed unit: input/output schema, an execute function, optional `__import__` code execution) is a clean composable primitive. The execution endpoint design exposes blocks as versioned, installable units. This is the same fundamental primitive as n8n's sub-nodes but earlier and more academically framed.
- **Caveat:** the audit-worthiness is dominated by **CVE-2025-1040** (SSTI → RCE in `AgentOutputBlock` via Jinja2 unsandboxed rendering, fixed in 0.4.0) and **CVE-2026-24780** (block-execute-by-UUID endpoint skips the `disabled` flag → RCE on default self-hosted deployment with Supabase signup enabled, fixed in `autogpt-platform-beta-v0.6.44`). Both are *direct* exfiltration primitives on the default self-hosted deployment. The product has been *breached in production-style ways* twice, and the second one specifically hit the default-install self-hosted path. The community edition is not safe to expose without a thorough review of the install-time defaults.
- **Citations:** CVE-2025-1040 — `https://nvd.nist.gov/vuln/detail/CVE-2025-1040`; CVE-2026-24780 — `https://nvd.nist.gov/vuln/detail/CVE-2026-24780`; vulnerable code paths cited in the NVD entries (e.g. `autogpt_platform/backend/backend/api/external/v1/routes.py:79-93`).
- **Marketing fluff to flag:** "Create, deploy, and manage continuous AI agents that automate complex workflows" — true in the literal sense, but the deployment defaults are the active threat surface. Treat *every* AutoGPT self-hosting guide older than 2026-06 as dangerous.

| **AutoGPT** | Partial — block-by-UUID endpoint design; the `disabled` flag exists (CVE-2026-24780 was caused by it being *ignored*) | Not documented | Limited — no platform-wide sandbox; `__import__()` in `BlockInstallationBlock` is the historical RCE path (CVE-2025-1040) | No | No — AutoGPT Platform has not published trifecta-aware guidance |

Two patterns to call out:

1. **The denylist problem.** OpenCrust, AnythingLLM, OpenHands' `PatternSecurityAnalyzer`, and the `InputValidator` family all rely on *known-bad patterns* to detect prompt injection. The 2025-10 paper "The Attacker Moves Second" (arXiv 2510.09023, 14 authors across OpenAI/Anthropic/Google DeepMind) and Meta's "Agents Rule of Two" both conclude that detection-based defenses are not reliable. Willison summarized this in 2025-11: "prompt injection remains an unsolved problem, and attempts to block or filter them have not proven reliable enough to depend on" (referring to both papers, `https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/`).
2. **The capability-tracking gap.** The only published production-grade system that *tracks taint through data flow* is CaMeL (arXiv 2503.18813, Google DeepMind + Google Research + ETH Zurich, code at `https://github.com/google-research/camel-prompt-injection`), which is research code, not a self-hostable platform. None of the 12 platforms in this audit implements capability-passing in the CaMeL sense. ZeroClaw's PR #2663 is the closest: it removes tool *classes* from the registry, which is a coarse-grained analog of capability revocation but not the same thing.

## 3. The real engineering frontier — and who is actually pushing it

The field's engineering frontier in 2026 is in four places:

### 3.1 Trusted-gateway / untrusted-execution splits
- **Who:** Google DeepMind (CaMeL — Privileged LLM (P-LLM) generates *code*; Quarantined LLM (Q-LLM) parses untrusted content into typed values; the interpreter enforces data-flow capabilities). Code: `https://github.com/google-research/camel-prompt-injection`. Paper: arXiv 2503.18813. As of 2026 the implementation is research-grade (single user, single intent, Python subset).
- **Adjacent:** the `lasso-security/mcp-gateway` family — sits between LLM and MCP servers, classifies tools along the trifecta axes, blocks the third condition from aligning in a single session. Show HN: `https://news.ycombinator.com/item?id=45223102`. The `Edison-Watch/open-edison` writeup is the clearest public articulation of the gateway-blocking-the-trifecta idea. *Treat as research, not as production hardening.*
- **Self-hostable platforms that have *any* form of this:** none. Hermes Agent's "context file injection protection" is the closest a self-hostable platform gets: it blocks specific files from the prompt. CaMeL's *capability-tagged values* are not in any audited platform.

### 3.2 Deferred tool loading / context economy
- **Who:** Anthropic (`advanced-tool-use-2025-11-20` beta: `ToolSearchToolBm25_20251119` with `defer_loading: true`; Python `tool_search_tool_bm25_20251119` class exposes `defer_loading` boolean — "If true, tool will not be included in initial system prompt. Only loaded when re[turned via tool_reference from tool search]" per `https://www.rubydoc.info/github/anthropics/anthropic-sdk-ruby/main/Anthropic/Models/ToolSearchToolBm25_20251119`; Claude Code v2.1.69 (March 2026) extended this to built-in system tools, reducing system-tools context from ~14-16k tokens to ~968 — `https://github.com/anthropics/claude-code/issues/31002`). GitHub Copilot CLI has the same `deferTools` knob (`https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/agents/copilot-cli/tool-search`).
- **Spec:** MCP SEP-1821 (Dynamic Tool Discovery, `https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1821`) — extends `ListToolsRequestParams` with an optional `query` string, plus `ServerCapabilities.tools.filtering`. Status: draft, with PR #1822.
- **Anthropic's own numbers** (from the SDK discussion): up to 85% reduction in tool token usage; Opus 4.5 tool-selection accuracy goes 79.5% → 88.1% with on-demand discovery.
- **Self-hostable platforms that have any form of this:** Hermes Agent has *toolset* gating (CLI/Telegram/Desktop presets like `hermes-cli` / `hermes-telegram` / `mcp-<server>`), which is the same primitive at a *coarser* granularity — pick the set, not the tool. ZeroClaw PR #2663 narrows the *per-agent* set, same idea. None of the audited platforms implements per-tool deferred loading behind a `ToolSearch` (the Anthropic / MCP approach). MCP-spec-side, the `paularlott/mcp` Go SDK ships a `discovery` package that does this at the server level (`https://pkg.go.dev/github.com/paularlott/mcp@v0.8.1/discovery`).

### 3.3 Deterministic policy at the action boundary
- **Who:** OpenHands SDK (the only one of the audited platforms with a real, *published*, *composable* `SecurityAnalyzer` enum and a `ConfirmationPolicy` enum — `https://docs.openhands.dev/sdk/guides/security`). The composition (`EnsembleSecurityAnalyzer` = `PolicyRailSecurityAnalyzer` + `PatternSecurityAnalyzer`) is a real design primitive. **But** the docs are explicit: this is a *deterministic action-boundary control*, not a sandbox and not a prompt-injection solution.
- **Adjacent:** OwnPilot's typed `RiskAssessment` against an autonomy level (numeric × numeric), which is the same idea at a less mature stage of implementation.

### 3.4 Memory architecture as a trust primitive
- **Who:** Letta (MemFS, git-tracked context, sync to a custom GitHub repo, `/sleeptime` dreaming, `/doctor` memory-quality audit, `/palace` view, mods). This is the only audited platform that treats *memory itself* as the auditable, branchable substrate. The innovation is not "agents that remember" — every audited platform has memory. The innovation is *content-addressable, branchable memory that the agent and the operator can both inspect and rewind*.
- **Adjacent:** Hermes Agent's "self-improving learning loop" / "creates skills from experience" is *not* on the frontier because skills are markdown files in a directory, not a content-addressed substrate.

### 3.5 The (mostly invisible) frontier — capability-based data flow in production
- CaMeL (arXiv 2503.18813) is the reference. "Operationalizing CaMeL" (arXiv 2505.22852) is the 2026 follow-up that names the *open* problems: side-channels, policy sprawl, latency cost. None of this has shipped in a self-hostable agent platform as of October 2026.

## 4. What nobody has solved

These are the open problems in the field as of 2026-10. I label each as "nobody has solved" only if the literature and the platforms I audited are all silent on it.

### 4.1 Reliable prompt-injection detection
- **Status:** unsolved. Meta's "Attacker Moves Second" (arXiv 2510.09023, 14 authors across OpenAI/Anthropic/Google DeepMind) is the most current negative result. Willison's reading: "prompt injection remains an unsolved problem, and attempts to block or filter them have not proven reliable enough to depend on." Anthropic, OpenAI, and Google DeepMind all signed the conclusion. The "lethal trifecta" remains lethal.
- **Where the literature stands:** every detection-based defense (denylist, perplexity, canary tokens, fine-tuned classifiers) is bypassable. The most recent general-purpose proposal is CaMeL (don't detect, contain) and the "Rule of Two" (don't try; pick two of three properties per session).

### 4.2 Side-channel exfiltration through agents that *seem* permission-bounded
- CaMeL notes data-flow manipulation through the Q-LLM as a residual risk. "Operationalizing CaMeL" explicitly lists side-channels as an open problem. No platform addresses them.

### 4.3 Capability tracking across *untrusted* code execution
- OpenHands' analyzer is at the *tool-call* boundary. The capability question is what *the tool itself* can do once invoked. A `file_read` tool can read any path the process can reach. A `web_fetch` tool can hit any URL the process can reach. No platform in the audit treats the *tool's actual reach* as a separate capability from the tool's *call*.

### 4.4 Multi-agent composition under the Rule of Two
- The Rule of Two is *per session*. Most multi-agent systems (AutoGen's GroupChat, CrewAI, Hermes Agent's `delegate_task`, OpenCrust's heartbeat model, OwnPilot's Subclaw) compose agents across sessions. The trifecta risk *compounds* across the composition. None of the audited platforms explicitly enforces the Rule of Two *across* the agent tree.

### 4.5 Replayable, diffable, *content-addressed* memory with privacy-aware redaction
- Letta MemFS gets the first two. The third (privacy-aware redaction) is not solved — once secrets land in a git-tracked memory block, they are in history. OwnPilot has a `privacy/redactor.ts` (per the architecture doc test list) but it operates at prompt time, not at write time. Anything that ever gets into the memory block is in the block's history forever.

### 4.6 A safe default for the lethal-trifecta
- The hard problem. The most defensible position in 2026 is the *Rule of Two*: no single agent session has all three of {untrusted input, private data, external comms}. Anthropic, OpenAI, Google DeepMind, and Meta researchers all converge on this. The user-facing consequence: any agent that reads your email, has access to your files, and can call an API needs a *fresh session* (or human-in-the-loop) for the trifecta intersection. The UX is bad; the alternative is worse. The unsolved engineering problem is the *automated* Rule of Two enforcement — tools that classify themselves as trifecta-bearing and force a session boundary before the third property is acquired.

### 4.7 Production-grade CaMeL
- The 2025 paper is research code. The 2026 follow-up notes the latency cost (Q-LLM effectively doubles model invocations), the policy-spec sprawl, and the side-channel risks. Nobody has shipped a self-hostable product with CaMeL's data-flow guarantees.

## 6. Bottom line

- **Most genuinely novel in self-hostable form:** Letta's MemFS (memory as a content-addressed, branchable, auditable substrate). Hermes Agent's hook/denylist combination on context files. OpenHands' composable `EnsembleSecurityAnalyzer` with honest limitations documentation.
- **Most over-marketed:** OpenClaw ("secure by design" contradicted by CVE volume), ZeroClaw ("zero overhead" contradicts "agent runtime"), AutoGPT ("create, deploy, manage continuous AI agents" — defaults ship RCE vectors in 2025-1040 and 2026-24780).
- **Real engineering frontier:** capability-based data flow (CaMeL and descendants) and deferred tool loading (Anthropic's `defer_loading`, MCP SEP-1821). Neither is in any audited self-hostable platform.
- **Nobody has solved:** reliable prompt-injection detection (confirmed by joint OpenAI/Anthropic/Google DeepMind/Meta position); side-channels through capability-bounded tools; multi-session Rule of Two; production-grade CaMeL. The *lethal trifecta* is, as of 2026-10, still lethal.
